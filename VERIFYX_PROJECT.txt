VERIFYX — PROJECT MASTER DOCUMENT
===================================

PROJECT
VERIFYX

TAGLINE
POINT. VERIFY. FIX. VERIFY AGAIN.

PURPOSE
Build a phone-first, offline-first AI system that verifies real-world workplace conditions against predefined standards.

1. WHAT WE ARE BUILDING
-----------------------
VERIFYX turns a smartphone into a physical-world verification tool.

An employee points the phone at a workplace environment.
VERIFYX observes the environment.
AI detects relevant objects/conditions.
A rules engine compares observations against predefined standards.
The system identifies PASS / FAIL / WARNING conditions.
The employee fixes an issue.
VERIFYX scans again and verifies the correction.
A report/evidence record can be generated.

Core loop:

POINT
  ↓
VERIFY
  ↓
FIX
  ↓
VERIFY AGAIN

Initial use case:
WORKPLACE SAFETY VERIFICATION

Initial checks:
- Fire Extinguisher
- Emergency Exit
- Safety Sign
- Clear Pathway
- Required Equipment

2. WHY WE ARE BUILDING IT
-------------------------
Businesses often rely on paper checklists, photos, manual observation, experienced supervisors, and manual reporting for physical inspections.

Problems:
- Inspections can be slow.
- Different employees can interpret standards differently.
- Issues can be missed.
- Evidence can be disconnected from the checklist.
- Supervisors may need to manually review photos.
- Fixes may not be verified immediately.
- Digital standards still require manual comparison with the physical world.

VERIFYX aims to close this gap:

DIGITAL STANDARD
      ↓
PHONE CAMERA
      ↓
AI OBSERVATION
      ↓
RULE VERIFICATION
      ↓
ACTIONABLE RESULT
      ↓
FIX
      ↓
RE-VERIFICATION

3. PRODUCT PHILOSOPHY
---------------------
Complex technology underneath.
Extremely simple experience outside.

The employee should only need to understand:

START
SCAN
SEE ISSUE
FIX
VERIFY AGAIN

The employee does not need to understand AI, computer vision, models, APIs, spatial computing, or rules engines.

4. END GOAL
-----------
The end goal is not simply a camera app.

The end goal is a reusable physical-world verification platform.

Architecture:

PHONE CAMERA
     ↓
AI / COMPUTER VISION
     ↓
SPATIAL / CONTEXT UNDERSTANDING
     ↓
RULE ENGINE
     ↓
VERIFICATION RESULT
     ↓
EVIDENCE
     ↓
REPORT / BUSINESS WORKFLOW

The first use case is workplace safety. The architecture should later be reusable for other business verification scenarios.

Possible future areas:
- Store readiness
- Workplace inspection

- Compliance-style checklists
- Operational readiness
- Asset presence verification

For the hackathon, keep the scope focused.

14. AI MODEL DIRECTION
----------------------
Prioritize:
- Lightweight models
- Open-source models
- Local inference
- Fast inference
- Android compatibility
- Low memory usage
- Practical detection accuracy

Model families to evaluate:
- Lightweight YOLO-family models
- Mobile-friendly vision models
- ONNX-compatible models
- TensorFlow Lite-compatible models
- Qualcomm-compatible inference paths

Model selection criteria:
1. Accuracy for required objects
2. Inference speed
3. Model size
4. Android compatibility
5. Offline operation
6. Deployment simplicity
7. License suitability

Do not select a model just because it is popular.

15. RULE ENGINE
---------------
AI should not decide the complete business result by itself.

AI = perception
Rules = business logic

Example:

AI:
fire extinguisher detected

Rule:
fire extinguisher must be present and accessible

Result:
PASS

Another example:

AI:
fire extinguisher detected

Context:
access area blocked

Rule:
required equipment accessible = false

Result:
FAIL

16. RESULT TYPES
----------------
Support:
PASS
FAIL
WARNING
NOT_DETECTED
NEEDS_REVIEW

Examples:
PASS = requirement satisfied.
FAIL = requirement violated.
WARNING = possible issue.
NOT_DETECTED = required object not found.
NEEDS_REVIEW = insufficient confidence/context.

17. CONFIDENCE HANDLING
-----------------------
Do not blindly trust AI.

High confidence:
Potential automatic verification.

Medium confidence:
WARNING / NEEDS_REVIEW.

Low confidence:
NOT_DETECTED / NEEDS_REVIEW.

The final product should communicate uncertainty rather than pretend AI is perfect.

18. EVIDENCE SYSTEM
-------------------

Possible evidence:
- Camera frame

20. OFFLINE-FIRST PRINCIPLE
---------------------------
Core verification should not require internet.

Benefits:
- Works with poor connectivity
- Less data transfer
- Lower latency
- Better reliability
- More privacy
- Local inference

Core local functions:
Camera
AI
Rules
Basic evidence

Internet should be optional for later workflows.

21. PRIVACY PRINCIPLE
---------------------
Do not make the core verification dependent on sending camera footage to a remote AI API.

Preferred:
Camera
 ↓
Local processing
 ↓
Local result

Use accurate claims such as:
"Designed for local/offline verification."

Do not claim "100% private" unless the implementation actually guarantees it.

23. iQOO / HACKATHON STRATEGY
----------------------------
The final product must run on the iQOO phone.

The phone matters because:
- Camera captures the physical environment.
- Local AI can process the scene.
- Mobile is the primary interaction.
- Local processing can reduce latency.
- The phone becomes the inspection tool.

Use public developer-accessible capabilities.

Do not depend on undocumented/private iQOO APIs.
Do not claim private hardware access unless it is actually available.

24. AR STRATEGY
--------------
AR is an enhancement, not the foundation.

Core verification must work without AR.

Possible AR later:
- Anchor detected objects
- Show PASS/FAIL labels
- Highlight obstructed areas
- Guide employee toward an issue
- Show verification zones
- Show FIXED state after re-scan

If AR becomes unstable or consumes too much time, remove it from the core flow.

25. NO EXTERNAL HARDWARE
------------------------
The project should not require:
- Arduino
- Raspberry Pi
- External sensors
- Special cameras
- Custom electronics
- Miniature physical props

The phone should be the main interface and hardware.

26. BUSINESS VALUE
------------------

27. CORE DIFFERENTIATOR
-----------------------
The concept is NOT simply:
"AI looks at a camera."

The important workflow is:

PHYSICAL WORLD
      ↓
OBSERVE
      ↓
COMPARE AGAINST STANDARD
      ↓
IDENTIFY DEVIATION
      ↓
TAKE ACTION
      ↓
VERIFY AGAIN

The product closes the loop.

Detection alone is not the final product.

Verification + correction + re-verification is the product loop.
